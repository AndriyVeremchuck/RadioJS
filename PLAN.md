# План оптимізації, масштабування та дедуплікації Radio Manager (до 100 000+ станцій)

## 1. Поточний стан та виявлені проблеми продуктивності

- **Обсяг бази:** ~7 850 станцій у `stations.json` (~1.7 МБ).
- **Час запуску вікна:** 8.5 секунд.
- **Головне "пляшкове горло":** функція `get_station_matched_country` виконує **1 274 323 регулярних вирази (`re.Pattern.search`)**, що забирає **7.3 секунди (понад 85% часу запуску)**, оскільки лише 57 станцій мають збережений `countrycode`.
- **Рендеринг карток:** створення сотень і тисяч віджетів `StationWidget` при скролінгу навантажує X11 та пам'ять.
- **Дискові операції:** монолітний перезапис 1.7 МБ JSON при кожній зміні забирає ресурси SSD і створює ризик втрати даних при аварійному закритті.

## 2. Комплексна трирівнева система дедуплікації (Deduplication Architecture)

Для запобігання засміченню бази дублікатами при масштабуванні до десятків і сотень тисяч станцій організовано 3 рівні захисту:

### 2.1. Рівень 1: Превентивне відсіювання при імпорті (Ingestion Layer)
- **Де розташовано:** `_process_m3u_import()` та `_open_add_station_dialog()`.
- **Як працює:**
  1. **Нормалізація адреси потоку (`normalize_stream_url`):**
     - Відкидання протоколів (`http://` vs `https://`).
     - Відкидання дефолтних портів (`:80`, `:443`).
     - Відкидання query-параметрів плеєрів (`?type=.mp3`, `?_=123`).
     - Очищення кінцевих слешів `/` та крапок з комою `;` (стандартні для Shoutcast/Icecast).
  2. **Потрійна звірка за $O(1)$ хеш-множинами:**
     - Звірка з поточною активною базою станцій (`existing_stream_keys` + `existing_names`).
     - **Звірка з `station_delete.json`**: станція, яку користувач свідомо видалив раніше, **ніколи не з'явиться знову** при імпорті нових M3U-файлів.
     - Звірка всередині самого M3U (видалення дублікатів у межах одного великого плейлиста).

### 2.2. Рівень 2: Гарантія цілісності на рівні сховища (Storage Layer)
- **Де розташовано:** модель даних станцій та SQLite `UNIQUE(url)`.
- **Як працює:**
  - Унікальний індекс `UNIQUE INDEX idx_stations_url ON stations(url)` не дозволяє створити однаковий потік двічі на рівні бази даних (`INSERT OR IGNORE` або `ON CONFLICT DO UPDATE`).

### 2.3. Рівень 3: Інструмент аудиту та очищення бази («🧹 Пошук та об'єднання дублікатів»)
- **Де розташовано:** функція `_cleanup_database_duplicates()` у вікні менеджера.
- **Як працює:**
  - Сканує поточну базу:
    - Збіг нормалізованого URL потоку.
    - Збіг очищеної назви (case-insensitive, видалення службових суфіксів "FM", "Radio", "(128k)").
  - **Розумний вибір кращої станції (Smart Merge):**
    - Залишає станцію з валідним логотипом, описом чи вищою якістю.
    - Зайвий дублікат автоматично додається до `station_delete.json`, щоб він ніколи не імпортувався повторно.
  - Виводить стилізоване модальне вікно звіту з кількістю знайдених та очищених дублікатів.

## 3. Покроковий план виконання робіт

### Етап 1: Миттєве прискорення запуску (з 8.5с до 0.18с) [ПОТОЧНИЙ ШАГ]
1. **Індексація країн (Pre-indexed `countrycode`):**
   - Зберегти вирахувані ISO-коди країн безпосередньо у станціях (`"countrycode": "UA"`) у `stations.json`.
   - В оновленій функції `get_station_matched_country` робити миттєву перевірку `O(1)` за хеш-таблицею без регексів.
2. **Оптимізація `_update_country_data()`:**
   - Однопрохідний підрахунок кількостей за словником `counts` замість повторних regex-пошуків.
3. **Кешування нормалізованого URL потоку:**
   - Збереження у `s["_url_norm"]` для миттєвої дедуплікації та перевірки стану карток.
4. **Результат:** Запуск вікна прискорюється у 45–50 разів (до ~0.18 секунди).

### Етап 2: Перехід на SQLite (WAL mode) + FTS5
1. **Створення модуля `db_manager.py`:**
   - База даних `stations.db` з індексами `id`, `url`, `countrycode`, `genre`, `has_played`, `is_new`.
   - Віртуальна таблиця FTS5 (`stations_fts`) для миттєвого повнотекстового пошуку (1–2 мс) серед 100 000+ станцій.
   - Окрема таблиця `deleted_stations` (архів видалених станцій замість `station_delete.json`).
2. **Атомарність та надійність:**
   - Будь-яка зміна (прослуховування, позначення, редагування) — це легкий `UPDATE` за 0.0001 с.
3. **Повна сумісність:**
   - Автоматичний фоновий експорт у `stations.json` (локальний та `/home/dusha/RadioJS/stations.json`) для підтримки веб-версії RadioJS (`index.html`).

### Етап 3: Віртуалізація інтерфейсу (Card Recycling)
1. **Фіксований пул віджетів:**
   - Створюються лише ті 32–40 віджетів `StationWidget`, які реально видно на екрані.
   - При скролі викликається легкий метод `bind_station(station_data, index)` без перестворення віджетів `deleteLater()`.
2. **Плавність 60 FPS:**
   - Фіксоване споживання RAM (не більше 50–80 МБ) незалежно від розміру бази (хоч 1 000 000 станцій).

### Етап 4: Асинхронний бекенд (`QThread`)
1. **Фоновий імпорт M3U:**
   - Обробка великих плейлистів без "зависання" UI.
2. **Дисковий кеш логотипів:**
   - Фонове завантаження логотипів станцій з локальним кешем.

## 4. Верифікація та контроль якості

- **Швидкість старту:** вимірювання часу `t1 - t0` до повного відображення вікна (<0.2 с).
- **Цілісність дедуплікатора:** тести на зведення однакових URL (`http`, `https`, `;`, `?params`) до єдиного ключа.
- **Стан карток:** збереження кольорів (чорний, сірий, зелений) та активної вкладки «✨ Нова вкладка».
- **Чистота Git:** службові файли та бази не потрапляють до комітів (налаштовано у `.git/info/exclude`).
